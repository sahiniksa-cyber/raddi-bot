# Instruction Routing Layer + Decision Context — تصميم (Multi-Tenant)

**التاريخ:** 2026-08-13
**الحالة:** تصميم معتمد من المالك — **التنفيذ بعد دمج PR #176** (محرّك حالة المحادثة). لا migrations ولا تغييرات production قبل الدمج والأمر الصريح.
**المبدأ الحاكم:** عام تمامًا، بلا أي hardcoding لمتجر/منتج بعينه. المحادثات (برو/Adobe...) حالات Regression فقط.

---

## 1. المشكلة (من Audit ميزة "تعديل البوت من الواتساب")

- ميزة التعديل تكتب في أربع وجهات فقط: `botInstructions` (نص حر)، `products`، `autoReplyKeywords`، `doNotReplyList`. **لا وجهة منظّمة للتصعيد إطلاقًا** (`escalationContacts` تُقرأ فقط).
- المخطِّط (`ai-client.js:746`) يُصنّف **أي توجيه سلوكي/تصعيدي كـ`prompt` نص حر**. فالتعليمات التشغيلية (تصعيد/إجراء/SLA/منع) تتكدّس في `botInstructions`.
- **النص الحر لا يتحوّل لسياسة منظّمة.** «حوّل لسعود» تبقى جملة؛ إن أصدر الـLLM `[تحويل:سعود]` وسعود ليس جهة منظّمة → **التصعيد يُلغى بصمت** والعميل وُعِد بالتحويل (عطل أمان).
- **`botInstructions` ≥ 80 حرفًا يصبح قاعدة البرومنت كلها** (`ai-client.js:368-370`) — تعديل تاجر صغير يسيطر على عقل البوت كاملًا. **مشكلة تصميم بحد ذاتها يجب أن تنتهي.**
- **لا طبقة تنفيذ Actions** — القدرة الوحيدة تصعيد عبر `[تحويل:]`؛ أي «تم رفع/إلغاء» وعد نصّي لا إجراء.

---

## 2. الطبقة الجديدة: Instruction Routing Layer

كل تعديل يُدخله التاجر (واتساب **أو** داشبورد) يمرّ أولًا بمصنِّف إلى **٧ فئات**، ثم يُوجَّه للطبقة المنظّمة الصحيحة:

| الفئة | تعريف | الوجهة المنظّمة |
|---|---|---|
| **Style** | نبرة/شخصية/تنسيق/إيموجي/طول | `replyStyle.*` + persona (القسم الوحيد المسموح في `botInstructions`) |
| **Knowledge** | حقائق (منتجات/أسعار/مواصفات) | `products` / قاعدة معرفة منظّمة |
| **Policy** | سياسات المتجر (استرجاع/شحن/دفع...) | مخزن سياسات منظّم (يُسترجع RAG) |
| **SLA-Time** | وعود زمنية («التفعيل خلال ١٢ ساعة») | **سياسة زمنية قابلة للحساب** (لا جملة يرميها الـLLM) |
| **Escalation** | توجيه/تحويل لجهة | `escalationContacts` + **قاعدة تصعيد** (شرط → جهة حقيقية) |
| **Action** | إجراء تنفيذي (صعّد/ألغِ/عدّل/أرسل/راجع) | **Action policy** — لا يُعدّ منفَّذًا إلا بعد Tool/Action ناجح |
| **Prohibition** | منع («ممنوع/لا ترد/لا تذكر») | `replyStyle.avoidPhrases` / سياسة منع منظّمة |

المصنِّف حتمي (أنماط عامة) + LLM مساعد عند الغموض؛ نفس المصنِّف يخدم مسار الواتساب والداشبورد (مصدر واحد للحقيقة).

---

## 3. القواعد الأساسية (قيود ملزمة من المالك)

1. **`botInstructions` = أسلوب/شخصية فقط.** لا تعليمات تشغيلية إطلاقًا.
2. **`botInstructions` لا يصبح قاعدة البرومنت مهما طال، ولا يطغى على منطق المنصة.** يُحقن كـ**قسم شخصية محدود** (بحدّ أقصى للطول/الموضع)، **تابعًا** لكتل المنصة التشغيلية (التصعيد/الحقائق/الحالة/SLA) لا فوقها. تُلغى قاعدة «≥80 حرفًا → القاعدة كلها».
3. **`escalationConditions` النص الحر يُستبدل تدريجيًا** بقواعد تصعيد منظّمة.
4. **SLA سياسة زمنية قابلة للحساب** (وقت مرجعي + مدة → حساب تلقائي للاستحقاق)، لا نص.
5. **Action لا يُعدّ منفَّذًا إلا بعد Tool/Action ناجح** (يمدّد أمانة الأدوات من المرحلة ١؛ الـLLM لا يعلن إنجاز إجراء نظامي).
6. **جهة تصعيد غير قابلة للحل → لا فشل صامت ولا وعد للعميل.** يُطلب من التاجر استكمال إعداد الجهة (رقم/قروب)، ويُمنع الـAI من وعد العميل بتحويل لا وجهة له.
7. **التعليمات القديمة لا تُحوَّل تلقائيًا.** الكاشف (منجز: `scripts/detect-operational-instruction-leaks.js`) يُخرج: `tenant + التعليمة + التصنيف المتوقع + مستوى الثقة + التحويل المقترح` → **مراجعة بشرية قبل أي تعديل** (تأكيد التاجر، بروح الخطوتين الحالية).

---

## 4. Decision Context موحّد قبل الرد

قبل السماح للـLLM بصياغة أي رد، يُجمَّع سياق قرار منظّم واحد:

```
DecisionContext = {
  conversationState,   // حالة منظّمة (المرحلة ١): open/resolved issues، active entity، known facts
  systemFacts,         // handoff pending، quota، auto-reply، سجلّات رسمية (لا LLM)
  timelineSLA,         // استحقاقات زمنية محسوبة من سياسات SLA (متأخر/ضمن المهلة)
  tenantPolicies,      // سياسات المتجر المنظّمة (استرجاع/شحن/دفع...) المطابقة للسؤال
  availableActions,    // ما يمكن تنفيذه فعلاً (Tools/Escalation targets قابلة للحل)
  missingData,         // نواقص تمنع الرد/الإجراء (رقم جهة، بيانات عميل)
  handoffState,        // حالة التصعيد (مسجّل/قيد المتابعة/محلول)
}
```

الـLLM يصيغ الرد **من** هذا السياق فقط. الفوائد: يمنع الوعود بلا إجراء (availableActions/missingData)، ويجعل SLA والحقائق النظامية مصادر حقيقة لا هبد، ويوحّد ما تراه كل الطبقات.

---

## 5. مسار التنفيذ (بعد الدمج، على مراحل خلف flags)

1. مصنِّف التعليمات (منجز جوهره في الكاشف) + وجهة تصعيد منظّمة قابلة للكتابة من الواتساب/الداشبورد.
2. تقليص `botInstructions` لقسم شخصية محدود تابع لكتل المنصة (إنهاء سيطرة ≥80).
3. سياسات SLA زمنية قابلة للحساب + حقنها في timelineSLA.
4. حارس جهة التصعيد غير القابلة للحل (طلب استكمال الإعداد + منع الوعد).
5. تجميع Decision Context موحّد قبل `getReply`.
6. ترحيل مُدقَّق للتعليمات القديمة (من مخرجات الكاشف، بتأكيد التاجر) — لا تلقائي.

كل مرحلة عامة، مطفأة افتراضيًا، قابلة للإطلاق مستقلة، بلا hardcoding.
