# تصميم مسار الرد الآمن المرتبط بالمنتج

## الحالة والقرار

طلب المستخدم يحدد التصميم ومعايير القبول صراحةً ويأذن بالبدء على فرع مستقل دون نشر. تم تقييم ثلاثة اتجاهات:

1. تحسين البرومنت فقط: مرفوض لأنه احتمالي ولا يمنع مزج المنتجات.
2. كتالوج حقائق منظم + ردود تجارية حتمية + فحص نهائي حتمي: معتمد.
3. تحويل جميع الردود إلى قوالب ثابتة: مرفوض لأنه يقتل الأسلوب الطبيعي ويصعب المحادثات العامة.

## البنية

### 1. كتالوج حقائق بإصدار ثابت

كل منتج يتحول إلى سجل منظم:

```text
productId
canonicalName
aliases[]
plans[] {
  planId
  label
  duration { value, unit }
  price { amount, currency }
  available
}
catalogVersion
```

المنتجات القديمة التي لا تحمل معرفًا تحصل على مفتاح legacy حتمي. عند أول حفظ لاحق تُحفظ معرفات UUID ثابتة. لا يُستخدم تشابه الاسم وحده لإثبات السعر.

### 2. تحديد المنتج من المحادثة

يقرأ resolver الرسالة الحالية وآخر أدوار الجلسة الحالية بالترتيب. الاسم الصريح في الرسالة الحالية أعلى أولوية، ثم آخر منتج صريح في السياق. إذا ظهر أكثر من منتج وكان السؤال لا يحدد المقصود، تكون النتيجة `ambiguous` ويُمنع ذكر سعر.

### 3. مسار الحقائق التجارية

أسئلة السعر والمدة والتوفر التي يمكن الإجابة عنها من الكتالوج تُجاب حتميًا من سجل المنتج، قبل الاعتماد على صياغة النموذج. النموذج يمكنه تحسين الأسلوب فقط، ولا يملك إضافة خطة أو رقم.

### 4. استخراج الادعاءات والتحقق

تُستخرج من كل جملة نهائية ادعاءات المنتج والخطة والمدة والسعر والعملة والتوفر. لا ينجح ادعاء تجاري إلا إذا طابق tuple واحدًا كاملًا في إصدار الكتالوج المستخدم. الرقم الموجود في منتج آخر لا يدعم الادعاء.

### 5. إصلاح محدود ثم إعادة فحص

الترتيب:

```text
draft
→ forbidden/identity guard
→ product-claim validation
→ length/style guard
→ duplicate/new-turn guard
→ full validation again
→ queued_for_send
```

إذا أمكن بناء جواب حتمي من الكتالوج يُستبدل الرد به، ثم تعاد كل الفحوص. وإلا يُرسل سؤال توضيح قصير. الحد الأقصى عملية إصلاح واحدة، ولا يستطيع تقييم LLM تجاوز مانع برمجي.

### 6. الكلمات والهوية

قائمة المنع الفعلية:

```text
platformIdentityAvoidList
+ defaultAvoidList
+ merchant.avoidWords
+ merchant.avoidPhrases
```

مع إزالة التكرار والتطبيع العربي والإنجليزي. كشف الهوية الآلية محظور افتراضيًا، ويمكن للتاجر تعطيله فقط بإعداد صريح. اسم الموظف لا يدخل البرومنت ولا الرد إلا إذا كان `employeeNameEnabled === true`.

### 7. الطول والتكرار

وضع `short` يفرض حدود أحرف وجمل وأسطر. الاختصار يتم على وحدات جمل، مع الحفاظ على روابط وحقائق المنتج، ثم يعاد الفحص.

قرار suppress مسموح فقط عندما لا توجد رسالة عميل جديدة، أي retry لنفس الإرسال. إذا توجد رسالة جديدة، يُنتج رد مختصر أو سؤال توضيح ولا يُترك العميل صامتًا.

### 8. التدقيق والإصدارات

جدول `product_catalog_versions` يحتفظ بنسخة المنتجات ورقم الإصدار والتغيير. جدول `ai_reply_traces` يحتفظ بالمراحل المنقحة من البيانات الحساسة لمدة 30 يومًا. كل رسالة صادرة تحمل `aiOperationId` و`productCatalogVersion` و`validatorVersion`.

### 9. العزل والتزامن

كل API داخلي جديد يستقبل scope غير اختياري:

```text
tenantId/userId + channelId + conversationId + customerId
```

مفاتيح الـqueue والـidempotency تتضمن هذا النطاق ومعرف الرسالة الواردة. كل كتابة/قراءة audit أو history أو catalog version تتحقق من النطاق نفسه.

## حالات الفشل

- فشل النموذج أو JSON: لا يرسل ادعاءً تجاريًا غير متحقق؛ يستخدم جوابًا حتميًا إن أمكن أو clarification.
- فشل فاحص LLM: الفحص الحتمي يستمر.
- فشل الفحص الحتمي: `blocked` ولا يصل إلى queue الإرسال.
- فشل Redis/DB: تبقى الحالة قابلة للاستعادة ولا يُعتبر الرد validated.
- retry/duplicate webhook: نفس idempotency key، بلا توليد أو خصم أو إرسال ثانٍ.
- نجاح إرسال واتساب وفشل التسجيل: سجل الإرسال الخارجي الدائم يمنع إعادة الإرسال.

## الخصوصية والاحتفاظ

- لا تحفظ مفاتيح API أو البرومنت الكامل إذا احتوى أسرارًا.
- تُحجب أرقام الهواتف والإيميلات من نصوص trace.
- النصوص الوسيطة تقص إلى حجم محدود.
- retention الافتراضي 30 يومًا مع cleanup batch.
- سجل نسخة الكتالوج يحتفظ بالحقائق التجارية ولا يحتاج رسائل العملاء.

## الاختبار

يبدأ كل إصلاح باختبار يفشل على `70f9fd1`. الاختبار النهائي يستخدم المسار الحقيقي من ingest إلى queue persistence ببدائل محلية لـPostgres/Redis فقط عندما لا يمكن تشغيل الخدمات، بينما محاكاة المنتج والفاحص تستخدم الكود الحقيقي وassertions حتمية بلا تقييم LLM.

## الإطلاق

لا نشر. التجهيز فقط: migrations forward/down، flags، shadow mode، متجر اختباري، progressive rollout وخطة rollback.
