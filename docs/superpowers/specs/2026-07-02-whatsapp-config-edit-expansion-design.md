# توسيع التعديل من الواتساب: المنتجات + الردود الفورية + الأرقام المحظورة

**التاريخ:** 2026-07-02
**الحالة:** تصميم للمراجعة
**يبني على:** ميزة تعديل البرومنت من قروب التصعيد (منشورة).

## الهدف
تمكين التاجر من تعديل **بيانات المتجر المنظّمة** من قروب التصعيد بأمر طبيعي موحّد:
- **المنتجات** (`products`): إضافة / تعديل (سعر، وصف، رابط، وصف مطوّل، متغيّرات) / حذف.
- **الردود الفورية** (`autoReplyKeywords`): إضافة / تعديل / حذف زوج (كلمة → رد).
- **الأرقام المحظورة** (`doNotReplyList`): إضافة / إزالة رقم.
- (يبقى **البرومنت** شغّالاً كما هو.)

البوت يفهم أي قسم يقصده التاجر، يعرض ملخصاً، يستأذن (تأكيد خطوتين)، وبعد التأكيد يطبّق فعلياً على البيانات المنظّمة — فيظهر في الداشبورد ويعتمده البوت مباشرة.

## المتطلبات

| # | المتطلب |
|---|---------|
| R1 | أمر طبيعي موحّد؛ البوت يصنّف القسم (منتجات/ردود فورية/أرقام/برومنت) والعملية (إضافة/تعديل/حذف). |
| R2 | توسيع كلمات الأوامر لتشمل أفعالاً طبيعية: `غيّر`/`غير`/`احذف`/`احظر`/`شيل`/`امسح` + الموجودة (`تعديل`/`عدّل`/`ضيف`/`أضف`/`برومنت`) — مع تسامح إملائي. |
| R3 | تحديد المنتج بالاسم؛ عند عدم الوجود أو تعدّد التطابق **يسأل ويتأكد** (ما يخمّن). |
| R4 | تأكيد خطوتين قبل التطبيق (يعرض ما سيتغيّر)، وأي صياغة تأكيد تُفهَم (المسار السريع + تصنيف الذكاء الموجود). |
| R5 | التطبيق على الحقل المنظّم الصحيح فعلياً؛ يظهر في الداشبورد ويعتمده البوت في ردوده. |
| R6 | تحقق من صحة البيانات: اسم منتج غير فارغ، رقم صالح (تطبيع مثل نظام الحظر)، كلمة+رد غير فارغين. |
| R7 | يعمل فقط من قروب تصعيد معرّف (نفس الحماية)، وأوامر/تأكيدات لا تُرسل للعميل، وfail-open. |
| R8 | تسجيل كل تعديل في السجل (القسم/العملية/الملخص/الحالة). |

## البُنى الحالية (مفحوصة)
- `products`: `[{ name(مطلوب), description, price, longDescription, url, variants:[{label, price}] }]` — يُعرّف بالاسم (لا id).
- `autoReplyKeywords`: كائن `{ [keyword]: reply }`.
- `doNotReplyList`: `[{ number(مطلوب), name }]`؛ التطبيع في `do-not-reply.js::normalizeNumber` (آخر ٩ أرقام).
- القراءة وقت التشغيل: `product-knowledge.js` (منتجات)، `platform-features.js::collectInstantReplies` (ردود فورية)، `do-not-reply.js::isCustomerBlocked` (أرقام). كلها تُقرأ طازجة عبر `resolveConfigForAI` كل رسالة.

## المعمارية

### 1. الكشف والتصنيف
- **الكلمات المفتاحية** (في `lib/prompt-edit-keywords.js`): تُضاف الأفعال الجديدة إلى `EDIT_KEYWORDS`. الكشف كما هو (أول كلمة + تسامح حرف).
- بعد الكشف: نداء ذكاء **`AIClient.planConfigEdit(config, request)`** يصنّف ويخطّط:
  - يستقبل: نص الطلب + قائمة أسماء المنتجات الحالية + مفاتيح الردود الفورية + أرقام الحظر (سياق ليحلّ الإشارات ويكتشف الغموض).
  - يرجّع كائناً (JSON صغير — القيم قصيرة، ليست نصاً طويلاً متعدد الأسطر):
    ```
    {
      "target": "prompt" | "products" | "instant_replies" | "do_not_reply",
      "action": "add" | "update" | "delete" | "merge",
      "summary": "<ملخص عربي سطر واحد>",
      "clarify": "<سؤال توضيحي عند الغموض/عدم الوجود — اختياري>",
      // حسب القسم:
      "product": { "name", "price?", "description?", "url?", "longDescription?", "variants?":[{"label","price"}] },
      "keyword": "...", "reply": "...",
      "number": "...", "name": "..."
    }
    ```
  - تحليل متسامح (نفس `_parsePromptEditJson`)؛ فشل التحليل → رسالة "ما فهمت، جرّب أوضح".
  - `target: "prompt"` → يُحوَّل للمسار الحالي `proposePromptEdit` (بروتوكول الفواصل المتين) بدل حشر التعليمات في JSON.
  - وجود `clarify` → البوت يرسله ويطلب توضيحاً (بدون تخزين معلّق).

### 2. التطبيق (دوال نقية قابلة للاختبار — `lib/config-edit-appliers.js`)
- `applyProductOp(products, op)` → `{ products, summary }` أو `{ needsClarify }`:
  - `add`: يلحق منتجاً جديداً (name مطلوب).
  - `update`: يطابق بالاسم (تطبيع + مطابقة تامة للاسم اللي حدّده الذكاء)؛ يدمج الحقول المُرسلة فقط (يحدّث السعر مثلاً ويترك الباقي)؛ المتغيّرات تُستبدل لو أُرسلت.
  - `delete`: يحذف المنتج المطابق.
  - عدم وجود تطابق (update/delete) → `needsClarify`.
- `applyInstantReplyOp(map, op)` → add/update يضبط `map[keyword]=reply`؛ delete يحذف المفتاح (بمطابقة متسامحة للمفتاح).
- `applyDoNotReplyOp(list, op)` → add يضيف `{number,name}` بعد التطبيع (بدون تكرار)؛ delete يزيل بمطابقة الرقم المُطبَّع (يعيد استخدام `normalizeNumber`).
- البرومنت: `applyInstructions` الحالية.

### 3. التخزين والتأكيد
- توسيع جدول `prompt_edit_requests` (migration idempotent):
  - `target TEXT NOT NULL DEFAULT 'prompt'`
  - `proposed_value JSONB` — القيمة الجديدة الكاملة للحقل المستهدف (مصفوفة المنتجات / كائن الردود / قائمة الأرقام / نص البرومنت).
  - (يبقى `proposed_instructions` للتوافق/السجل.)
- عند الاقتراح: نحسب القيمة الجديدة عبر الـ applier ونخزّنها في `proposed_value` مع `target` والملخص، الحالة `pending`.
- عند التأكيد: تطبيق عام حسب `target` → حقل:
  - prompt→`botInstructions`، products→`products`، instant_replies→`autoReplyKeywords`، do_not_reply→`doNotReplyList`.
  - تعميم `applyInstructions` إلى `applySectionValue(database, userId, field, value)` عبر `jsonb_set`.
- الإلغاء/المهلة/التذكير/تصنيف نية التأكيد: كما هي (مُعاد استخدامها).

### 4. الظهور والاعتماد
- الداشبورد يعرض التغيير فوراً (إصلاح `getConfig` الطازج — منشور).
- البوت يقرأ الأقسام طازجة كل رسالة (`resolveConfigForAI`) → يعتمد التغيير مباشرة.

## معالجة الأخطاء والحواف
- فشل الذكاء/تحليل غير صالح → "ما فهمت، جرّب أوضح"؛ لا معلّق.
- منتج غير موجود/متعدد → سؤال توضيحي (يعرض المرشّحين)؛ لا معلّق.
- بيانات غير صالحة (رقم فارغ/اسم فارغ) → رسالة خطأ واضحة؛ لا حفظ.
- حذف = محمي بتأكيد خطوتين.
- كل المعالج fail-open (لا ينكسر مسار الرسائل).

## الاختبارات (TDD)
- **appliers نقية**: إضافة/تعديل/حذف منتج (دمج السعر فقط، المتغيّرات، اسم غير موجود→clarify)؛ إضافة/تعديل/حذف رد فوري؛ إضافة/إزالة رقم مع التطبيع والتكرار؛ التحقق.
- **planConfigEdit**: تحليل JSON صغير لكل قسم + حالة clarify + توجيه prompt.
- **الخدمة**: توجيه كل target إلى الحقل الصحيح؛ التأكيد يكتب `proposed_value` في الحقل الصحيح؛ عدم الإرسال للعميل؛ الميزة معطّلة/قروب غير معرّف → تجاهل.
- **migration**: وجود العمودين.

## خارج النطاق (YAGNI)
- لا حذف/تعديل جماعي (منتج واحد لكل أمر).
- لا تعديل اسم المتجر/ساعات العمل/جهات التصعيد عبر الواتساب (الآن).
- لا استيراد قوائم كاملة.
