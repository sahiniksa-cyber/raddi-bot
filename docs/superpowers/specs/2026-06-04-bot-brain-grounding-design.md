# تصميم: عقل البوت — Grounding + Validation (ردّي)

**التاريخ:** 2026-06-04
**الحالة:** مُصادق عليه تجريبياً (3 زوايا تحقق مستقلة على gpt-4o)
**المنصة:** بوت واتساب AI متعدد المستأجرين (Node + Baileys + BullMQ + Postgres + Redis، Railway، الداشبورد jwap.net)

---

## 1. المشكلة (مُثبتة بالكود، لا نظرية)

التاجر يشتكي من شهرين:
1. البوت أحياناً **لا يذكر ما في الردود الفورية**.
2. أحياناً لا يقول أشياء **موجودة في البرومنت**.
3. مشاكل في الأسلوب وطول الكلام.

### الجذر المُكتشف (لا الأعراض)

`buildSystemPrompt` في [lib/ai-client.js](../../../lib/ai-client.js) **لا يقرأ `autoReplyKeywords` إطلاقاً**. الردود الفورية تُستهلك فقط في مسار منفصل `findAutoReply` ([src/services/bot/platform-features.js:8](../../../src/services/bot/platform-features.js)) الذي يطابق **substring حرفياً**. النتيجة:

- لو لم تطابق رسالة العميل الكلمة المفتاحية حرفياً → الرد الفوري لا يُرسل، **والـAI لا يعرف الجواب أصلاً** → يتهرّب ("بسأل المختص") أو يخترع.
- البرومنت نفسه عبارة عن **جدار نصي بصيغة توجيهات** ("افعل/لا تفعل") — النماذج تطيعه جزئياً.
- **لا توجد طبقة تحقق** بعد التوليد: الطول غير مفروض، اكتمال أجزاء السؤال غير مضمون، التصعيد احتمالي.

### الدليل التجريبي (gpt-4o، 3 وكلاء مستقلين، 3 مجابر متاجر)

| الزاوية | المجال | البوت الحالي | بعد حقن الردود |
|---|---|---|---|
| الردود الآلية (إعادة صياغة) | عطور | 23% (3/13) | **100%** (13/13) |
| سحب معلومات المنصة | إلكترونيات | 71% | **100%** |
| الاستهبال/التهرّب | كافيه | 50% فشل | **0% فشل** |

**ثغرتان اكتُشفتا أثناء التحقق (مهمتان):**
- **ث1 — الحقن قد يسبب اختراعاً:** وصف الردود المحقونة بأنها "مصدر حقيقة" رفع جرأة النموذج فجزم بميزة منتج غير مذكورة (مثال حقيقي: "الشاحن يدعم آيفون وسامسونج" رغم عدم ذكرها). فئة "الميزات غير المذكورة" تراجعت 100%→67%.
- **ث2 — الحقن وحده لا يكفي:** علامة التصعيد `[تحويل:]` احتمالية (سرّبت رقم المدير بدون علامة 1 من 3)، والسؤال المركّب قد يُتجاهَل جزء منه بصمت، والطول غير مفروض برمجياً.

## 2. الهدف ومعايير النجاح

**الهدف:** بوت "عنده عقل" — يجاوب من معرفة المنصة بثبات، لا يتهرّب عن معلومة متوفرة، لا يخترع، ويلتزم بالأسلوب والطول. يعمل لأي مجال متجر (multi-tenant) بدون كود مخصص لأي تاجر.

**معايير النجاح القابلة للقياس:**
- دقة الرد على الردود الفورية عبر إعادات الصياغة ≥ 95% (الحالي 23%).
- صفر اختراع أسعار/منتجات (الحفاظ على 100% الحالي في هذه الفئة).
- اختراع ميزات المنتجات لا يزيد عن الحالي (إغلاق ث1).
- ضمان التصعيد الحتمي 100% عند نية صريحة (إغلاق ث2).
- التزام الطول 100% (فرض برمجي).
- لا تدهور في زمن الرد المحسوس بشكل يضر التجربة.

**خارج النطاق (YAGNI):** إعادة كتابة واجهة الداشبورد، تغيير مزوّدي الـAI، نظام تدريب/fine-tuning.

## 3. المعمارية

أربع طبقات تُضاف حول الاستدعاء الحالي. تعمل بالترتيب على كل رسالة عميل (عدا Compiler الذي يعمل عند حفظ التاجر).

```
حفظ التاجر للبرومنت
   └─► [L0] Prompt Compiler  → compiled object مخزّن + تنبيهات حقول ناقصة (Phase 2)

رسالة عميل
   ├─► findAutoReply (حرفي، يبقى كاختصار سريع للمطابقة التامة)
   ├─► [L1] Retrieval Injector → يحقن السياسات المطابقة كـ <معرفة_سياسات_المتجر>
   ├─► [L2] Structured Prompt → أقسام XML بدل جدار نصي + few-shot
   ├─► [L3] LLM call (± tools حسب النموذج — Phase 2)
   └─► [L4] Validator + Repair → فحص ثم إصلاح مرة، وإلا fallback آمن
        └─► إرسال عبر WhatsApp
```

### حدود المكوّنات (كل واحد مسؤولية واحدة، قابل للاختبار منفصلاً)

| المكوّن | الملف | المسؤولية | يعتمد على |
|---|---|---|---|
| Retrieval Injector | `src/services/ai/knowledge-retrieval.js` (جديد) | يطابق سؤال العميل مع السياسات (fuzzy عربي مُطبَّع)، يرجّع كتلة نصية مُقيَّدة | config.autoReplyKeywords |
| Structured Prompt | `lib/ai-client.js` (تعديل `buildSystemPrompt`) | بناء البرومنت كأقسام XML واضحة + دمج كتلة الـretrieval | knowledge-retrieval, platform-features |
| Reply Validator | `src/services/ai/reply-validator.js` (جديد) | فحوصات حتمية بعد التوليد + قرار repair/fallback | config, المعرفة المطابقة |
| Prompt Compiler (P2) | `src/services/ai/prompt-compiler.js` (جديد) | تحويل نص التاجر لأقسام مخزّنة + تنبيهات | — |
| Tool layer (P2) | `src/services/ai/ai-tools.js` (جديد) | get_product / get_policy / escalate للنماذج القوية | products, policies |

## 4. تصميم الطبقات (Phase 1)

### L1 — Retrieval Injector

**المدخل:** `config`, نص رسالة العميل.
**المخرج:** كتلة نصية (قد تكون فارغة) تُدمج في البرومنت.

**الخوارزمية:**
1. طبِّع عربياً (نفس `normalizeArabic` في [post-process-reply.js](../../../lib/post-process-reply.js): توحيد الألف/التاء المربوطة/الياء، إزالة التشكيل).
2. لكل `(keyword, reply)` في `autoReplyKeywords`: احسب درجة صلة = تداخل tokens بين (سؤال العميل) و(الكلمة المفتاحية + نص الرد)، مع مرادفات شائعة محدودة (توصيل↔شحن، استرجاع↔إرجاع، كاش↔دفع نقدي).
3. رتّب تنازلياً. احقن أعلى **K=6** فقط بدرجة فوق عتبة دنيا، **وإن لم يتجاوز أي شيء العتبة احقن الكل إذا كان العدد ≤ 8** (الأعداد الصغيرة رخيصة وآمنة).
4. لو العدد الكلي للردود > 20: احقن المطابقات فقط (حل مشكلة قابلية التوسّع التي رصدها وكيل العطور).

**الكتلة المحقونة (مُقيَّدة — إغلاق ث1):**
```
<سياسات_المتجر_الجاهزة>
هذه سياسات عامة كتبها صاحب المتجر (شحن، دفع، إرجاع، حجز، أوقات، رسوم). إن خصّ سؤال العميل أياً منها، اعتمدها كمصدر حقيقة وصُغها بأسلوبك القصير، ولا تقل "بسأل المختص" لمعلومة موجودة هنا.
مهم: هذه سياسات فقط. مواصفات المنتجات وتوافقها وأي ميزة تقنية تبقى خاضعة لقاعدة عدم الاختراع — لا تجزم بميزة غير مذكورة صراحة في قائمة المنتجات.
- <reply_1>
- <reply_2>
...
</سياسات_المتجر_الجاهزة>
```

> ملاحظة: التسمية "سياسات" لا "معرفة مصدر حقيقة مطلقة" مقصودة — التحقق أثبت أن الصياغة المطلقة تسبب اختراع ميزات.

### L2 — Structured Prompt

إعادة هيكلة `buildSystemPrompt` من سلسلة نصية إلى أقسام XML محدّدة (النماذج تتبع البنية الوسومة أفضل من النص الحر):

```
<الشخصية>…</الشخصية>
<معلومات_المتجر>الاسم، الوصف، الأوقات…</معلومات_المتجر>
<المنتجات>…</المنتجات>
<المنتجات_المطابقة>…</المنتجات_المطابقة>   (موجود عبر buildRelevantProductContext)
<سياسات_المتجر_الجاهزة>…</سياسات_المتجر_الجاهزة>   (من L1)
<قواعد_الدقة>ممنوع الاختراع…</قواعد_الدقة>
<الأسلوب>اللغة، اللهجة، الطول، الإيموجي، النبرة، الترحيب، الخاتمة، التنسيق</الأسلوب>
<التصعيد>الجهات + الشروط + صيغة العلامة</التصعيد>
<أمثلة>2-3 محادثات نموذجية عامة (few-shot) تُظهر: الرد من السياسة، عدم اختراع ميزة، التصعيد الصحيح</أمثلة>
```

تعليمات المالك الطويلة (`hasLongCustomInstructions`) تبقى في الأعلى بأولوية مطلقة كما هي الآن.

### L4 — Reply Validator + Repair

**يعمل على ناتج النموذج قبل الإرسال.** فحوصات حتمية:

1. **الطول:** إن تجاوز `maxResponseLength` → repair بطلب اختصار، وإلا قصّ ذكي عند آخر جملة كاملة.
2. **اختراع سعر:** أي رقم يتبعه "ريال"/عملة في الرد يجب أن يطابق سعراً في قائمة المنتجات أو في السياسات المحقونة (مطابقة مُطبَّعة). وإلا → repair.
3. **كاشف التهرّب (cop-out):** إن احتوى الرد عبارة تأكيد-من-المختص ("أأكد لك"، "بسأل المختص"، "تسمح لي") **بينما** يوجد سياسة/منتج مطابق بدرجة عالية لم يُستخدم → repair بحقن الجواب مباشرة.
4. **اكتمال السؤال المركّب:** قسّم رسالة العميل على أدوات الربط/علامات الاستفهام إلى أسئلة فرعية؛ إن وُجد >1 سؤال وأحدها بلا أي مؤشر إجابة → repair بطلب تغطية كل الأجزاء.
5. **ضمان التصعيد:** إن كشف كاشف نوايا حتمي (regex: "أكلم/أبي/أحتاج" + "مدير/مسؤول/إنسان/موظف"، أو حجز عدد كبير، أو شكوى) نيةَ تصعيد **ولم** توجد علامة `[تحويل:]` → أضِف العلامة برمجياً (لا تعتمد على النموذج). **يمنع تسريب رقم بدون إشعار للمالك.**
6. **التنسيق/الكلمات الممنوعة:** يبقى عبر `stripAvoidedContent` الحالي.

**سياسة الإصلاح:** محاولة repair واحدة فقط (إعادة توليد بتعليمات محددة). فشلها → نرسل أفضل ناتج متاح أو fallback الآمن. **لا حلقة repair لا نهائية** (حماية latency).

## 5. تدفق البيانات (Data Flow)

```
ai-worker.processAiReply
  → resolveConfigForAI(userId)
  → findAutoReply(config, text)            # اختصار حرفي: لو طابق، أرسل النص الخام مباشرة (سرعة)
  → buildHistoryForReply(...)
  → AIClient.getReply(history, opts):
        knowledge = retrieveRelevantPolicies(config, lastUserText)   # L1
        system    = buildStructuredSystemPrompt(config, knowledge)   # L2
        raw       = call LLM (± tools)                               # L3
        final     = validateAndRepair(raw, {config, knowledge, text})# L4
        return final
  → storeAssistantMessage → enqueueOutgoingWhatsapp
```

**مواءمة المسارين (حسم ث المزدوج):** `findAutoReply` الحرفي يبقى للسرعة عند المطابقة التامة لرسالة واحدة. أما حين يدخل الـAI، فكتلة L1 هي المرجع — النموذج يعيد صياغتها بأسلوبه. لا تعارض: مسار واحد فقط ينفّذ لكل رسالة.

## 6. التنفيذ على مراحل (Rollout)

### Phase 1 (الإطلاق — يحل ≥80% ومُثبت تجريبياً)
- L1 Retrieval Injector (كتلة سياسات مُقيَّدة + فلترة/سقف).
- L2 Structured Prompt (أقسام XML + few-shot).
- L4 Validator (الفحوصات الستة).
- يعمل **لكل النماذج** (Gemini/GPT/Claude).
- خلف feature flags، آمن multi-tenant، لا كود خاص بأي تاجر.

### Phase 2 (بعد الإطلاق — للتوسّع والصرامة)
- L0 Prompt Compiler الكامل + تنبيهات الحقول الناقصة للتاجر.
- L3 Tool-Calling (get_product/get_policy/escalate) للنماذج القوية فقط — يجعل الاختراع مستحيلاً بنيوياً ويتوسّع لمئات المنتجات. (التحقق أثبت أنه ليس شرطاً للإطلاق: حقن L1 يضاهيه نصياً في الحالات العادية.)

## 7. الاختبار

- **وحدة:** `knowledge-retrieval` (تطبيع، صلة، سقف، فلترة)، `reply-validator` (كل فحص على حدة بمدخلات مُصطنعة لا تحتاج شبكة).
- **تكامل (offline):** بناء البرومنت لـconfig مرجعي والتأكد أن السياسات تُحقن وأن الأقسام موجودة — بدون استدعاء نموذج (مثل `tests/ai-client-prompt.test.js` و`ai-prompt-rules.test.js` القائمة).
- **تقييم (online، اختياري بمفتاح):** harness يعيد سيناريوهات الوكلاء الثلاثة (عطور/إلكترونيات/كافيه) ويقيس نِسَب النجاح مقابل العتبات في §2. لا يدخل CI (يحتاج مفتاح + تكلفة).
- **حواجز الانحدار:** اختبار يثبت عدم زيادة اختراع الميزات (سيناريو الشاحن/آيفون من ث1)، واختبار يثبت ضمان `[تحويل:]` عند نية صريحة (ث2).

## 8. المخاطر والمقايضات

| الخطر | التخفيف |
|---|---|
| الحقن يرفع جرأة النموذج → اختراع ميزات (ث1) | كتلة مُقيَّدة بـ"سياسات" + تحذير صريح + اختبار انحدار |
| كثرة الردود تضخّم البرومنت | سقف K=6 + فلترة بالصلة عند >20 |
| repair يزيد الlatency | محاولة واحدة فقط ثم fallback |
| كاشف النوايا يعطي false positives في التصعيد | regex محافظ + قابل للضبط، يُسجَّل للمراجعة |
| تعارض ردين فوريين متناقضين | Compiler (P2) يكشفه وينبّه التاجر؛ في P1 يُحقن الأعلى صلة |
