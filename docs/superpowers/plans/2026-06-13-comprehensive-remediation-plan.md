## 2) إجابة أسئلتك الخمسة مباشرة

**1. الأمان — هل ممكن اختراق المنصّة؟**
نعم، توجد **ثغرة واحدة حرجة فعلية** (SSRF في فاحص المتاجر — تاجر مسجّل يقدر يجبر الخادم يجلب خدمات داخلية/metadata السحابة على Railway) + **تثبيت جلسة** (session fixation) خطورته عالية. ما عدا ذلك الأساس قوي: كل استعلامات SQL مُعامَلة (لا حقن)، عزل بيانات التجار سليم، محتوى العميل مُهرَّب ضد XSS، مفاتيح API مشفّرة AES-256-GCM، كوكي الجلسة آمن. **قابل للإصلاح بالكامل في المرحلة 3.**

**2. التشغيل — الأخطاء والتأخير والتعليق:**
أكبر خطر **معماري**: كل التجار في **عملية واحدة** + `botCache` لا يُنظَّف (تسريب ذاكرة تدريجي → OOM يُسقط الجميع)، وعامل إرسال **واحد** (concurrency=1) ينتظر حتى 45 ثانية لبوت غير متصل فيؤخّر ردود **كل** التجار، و pool قاعدة بيانات صغير (10) مشترك. هذه تُعالَج بالمرحلتين 4 و5.

**3. تجربة العميل — السلامة وعدم التعليق:**
جيدة عموماً، لكن 3 ثغرات تضرّ العميل مباشرة: **رد مكرّر** عند فشل جزئي بعد الإرسال (ظهر فعلاً بالإنتاج)، **إسقاط رسالة** صامت عند تساوي نافذة الكتم 30د مع نافذة الانتهاء 30د، و**تسرّب علامة `[تحويل:]`** مشوّهة للعميل. تُعالَج في المرحلة 2.

**4. لو صارت مشكلة مع تاجر — وش نسوي كإدارة؟**
اليوم: **لا شيء عن بُعد** (3/10) — الحل الوحيد إعادة نشر المنصّة كلها (تضرّ الجميع) أو الطلب من التاجر. الحل = **لوحة تحكم التاجر للأدمن (المرحلة 1)** + دليل التشغيل (Runbook) في القسم 6. هذه أولويتك المعلنة ونبدأ بها.

**5. هل كل تاجر له نظامه الخاص؟ هل المتاجر متشابكة؟**
**بياناتهم معزولة تماماً** — مستحيل تاجر يشوف بيانات تاجر ثاني (كل جدول مربوط بـ `user_id`، كل المعرّفات UUID، مفاتيح وجلسات الواتساب منفصلة). **لكن تشغيلياً يتشاركون "أنبوباً" واحداً** (عملية + طابور). فشل أو حِمل تاجر واحد **لا يسرّب بياناته** لكن قد **يبطّئ أو يُسقط الباقين مؤقتاً**. أي: ليست شبكة متشابكة بالبيانات، لكنها سلة واحدة بالموارد. الحل الجذري طويل المدى في المرحلة 5 (توزيع التجار على نسخ).

## 4) خطط الحلول حسب المراحل (مع الضمانات)

### المرحلة 1 — لوحة تحكم التاجر للأدمن (أولويتك المعلنة) — يرفع جاهزية الأدمن من 3 إلى ~8/10
يغلق: ADM-1,2,3,4,6,7,8. الـ spec جاهز: `docs/superpowers/specs/2026-06-13-admin-merchant-control-panel-design.md`.

**تصحيح ربط مؤكَّد بالقراءة (2026-06-13):** مرِّر **`getUserBot` (async)** إلى `createAdminRoutes` — **وليس** `syncBotLookup`. السبب: `syncBotLookup` (server.js:781-784) **يرمي `'bot is not loaded yet'`** لأي بوت غير موجود في `botCache`، وأغلب التجار (الموقوفون أو غير المُستدعَين بعد الإقلاع) ليسوا في الكاش → استخدامه يكسر اللوحة لأي تاجر غير نشط. لذا تكون handlers الأدمن **async** و`await getUserBot(userId)` (يُنشئ ويحمّل عند الحاجة). (توصية agent جاهزية الأدمن باستخدام syncBotLookup **غير صحيحة** وصُحّحت هنا.)

**أثر جانبي مؤكَّد:** `load()` → `loadSessionState` (runtime-bot.js:284-294) يجدول `startBot('auto_recover')` تلقائياً عند `desired_state='running'`. فتح تشخيص تاجر "مفروض شغّال" قد يبدأ اتصاله — سلوك **صحيح ومطابق** لـ boot-recovery، وغير ضار؛ تاجر `desired_state='stopped'` لا يبدأ. يُوثَّق في الواجهة.

**إضافة من الفحص:** أضِف `isInConnConflictBackoff()` و`reconnectCount` إلى بطاقة التشخيص — لتمييز "عالق في backoff 440" عن "ساقط فعلاً".

| البند | الحل | الضمان |
|------|------|--------|
| ADM-2 | تمرير `syncBotLookup` ضمن `routeDeps` إلى `createAdminRoutes` | اختبار تركيب: المُحلّل مُمرَّر؛ مسار يستدعي بوت تاجر مستهدف |
| ADM-1,7 | مسارات `POST /api/admin/customers/:userId/bot/{restart,stop,clear-session}` + `GET .../bot/qr-image` تستدعي نفس دوال `RuntimeBot` بالـ userId | اختبار: كل زر يستدعي الدالة الصحيحة بالـ userId عبر mock؛ userId غير موجود → 404 |

## 5) ترتيب التنفيذ الموصى به

1. **المرحلة 1 (لوحة الأدمن)** — أولويتك، وأعلى أثر تشغيلي، وأقل خطر (طبقة جديدة لا تلمس الموجود).
2. **المرحلة 2 (تجربة العميل)** — CX-2 و CX-3 يضرّان العميل فعلاً الآن.
3. **المرحلة 3 (الأمان)** — SEC-1 أولاً (ثغرة فعلية)، ثم SEC-2.
4. **المرحلة 4 (نصف قطر العطل)** — تحسينات تشغيلية تمنع كارثة جماعية.
5. **المرحلة 5 (التوسّع)** — متوسطة المدى، تُنفَّذ تدريجياً.

**حوكمة لكل مرحلة:** كل بند يبدأ باختبار فاشل (TDD) → كود → اختبار أخضر → `node --test` كامل أخضر → دمج. **نشر مرّة واحدة لكل مرحلة** (لا churn). التغييرات الخطرة (OPS-2/3، ISO-3) خلف flags بيئية.

## 6) دليل التشغيل (Runbook) — ماذا تفعل الإدارة عند مشكلة تاجر

> بعد تنفيذ المرحلة 1 يصبح كل "الإجراء" زرّاً في لوحة الأدمن. قبلها، هذا ما يمكن فعله اليوم.

| المشكلة | الإجراء **بعد المرحلة 1** | الإجراء **اليوم (مؤقتاً)** |
|---------|---------------------------|----------------------------|
| بوت التاجر ما يرد | ابحث عن التاجر → بطاقة التشخيص → زر **إعادة تشغيل** | إعادة نشر المنصّة (يضرّ الجميع) أو الطلب من التاجر |
| عالق reconnecting/waiting_qr | زر **إعادة تشغيل** + راقب backoff في البطاقة | لا شيء عن بُعد |
| قفل عالق (stale lease) | زر **تحرير القفل** | انتظار انتهاء TTL أو جراحة DB يدوية |
| الرصيد خلص (صامت) | **موجود اليوم:** زر **شحن رصيد** | نفسه — متاح فعلاً |
| يحتاج إعادة ربط واتساب | زر **مسح الجلسة** (تأكيد) ثم **QR** | الطلب من التاجر |
| "البوت رد رد غلط" | (P2) عرض آخر رسائل التاجر للتشخيص | قراءة جداول DB يدوياً |
| انفصل فجأة (440/logged out) | التنبيه يصل تلقائياً + زر **تحرير القفل/إعادة تشغيل** | التنبيه يصل، لكن لا إصلاح عن بُعد |

**ملاحظة:** المراقبة والتنبيه تعمل اليوم فعلاً — المالك يُنبَّه على واتساب/إيميل عند سقوط أو فك ربط أي بوت (`unlink-alert.js`, `health-checks.js`). النقص في "ماذا أفعل عن بُعد" لا في "هل أعرف".

## 7) ملاحظات

- **Moyasar:** الكود خامل وآمن (يردّ 503 ما لم يُضبط السر، HMAC ثابت التوقيت، لا IDOR). الدفع فعلياً = تحويل بنكي + شحن يدوي. لا حاجة لإجراء أمني عاجل؛ يُوصى بإضافته لقوائم الاستثناء الصريحة (SEC-9) ثم حذفه لاحقاً كتنظيف.
- **نقاط القوة المؤكَّدة بالقراءة:** عزل بيانات ممتاز، SQL مُعامَل بالكامل، XSS مُحكم عبر `esc()`، تشفير مفاتيح AES-256-GCM، حارس تكرار الردود، طبقتا staleness، شبكة `process-safety`، مراقبة/تنبيه فعّالة.
