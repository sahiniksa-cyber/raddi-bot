# خطة الإطلاق والرجوع لمسار الرد الآمن

لا تنفذ هذه الخطة إلا بعد موافقة صريحة، وفي بيئة staging أولًا.

## شروط البدء

1. أخذ snapshot لقاعدة البيانات ونسخة من متغيرات Railway دون نسخ الأسرار إلى التقرير.
2. توثيق commit الإصدار ونسخة الكتالوج الحالية.
3. التأكد أن الفرع `codex/safe-reply-hardening` نظيف وأن الاختبارات والمحاكاة ناجحة.
4. إنشاء متجر اختبار مستقل وقناة ورقم WhatsApp اختباريين.

## ترتيب migrations

1. إنشاء `product_catalog_versions` وفهرسه وtrigger عدم التعديل أو الحذف.
2. تعديل فهرس `messages` إلى `(user_id, channel_id, provider_message_id)`.
3. إنشاء `ai_reply_traces` وفهارس النطاق والاحتفاظ.
4. التحقق read-only من الجداول والفهارس والـtrigger.
5. إبقاء `REPLY_TRACE_ENABLED=false` حتى اكتمال التحقق.

كل migration مضافة additive وقابلة للرجوع بملفات:

- `docs/migrations/rollback-product-catalog-versions.sql`
- `docs/migrations/rollback-message-provider-scope.sql`
- `docs/migrations/rollback-ai-reply-traces.sql`

## Shadow mode

1. تشغيل `node scripts/simulate-safe-replies.js` على snapshot من إعدادات متجر الاختبار بعد تنقيح أي بيانات حساسة.
2. مقارنة `originalDraft` مع `finalReply` وإحصاء أسباب block/repair/clarify.
3. تفعيل `REPLY_TRACE_ENABLED=true` في staging فقط بعد migration.
4. تشغيل worker اختبار لا يملك قناة إرسال حقيقية، ومراجعة traces لكل مرحلة.
5. لا يُسمح بمتابعة الإطلاق إذا ظهر فشل واحد في سعر/مدة/توفر/عزل/كلمة ممنوعة.

حمايات الحقائق الحتمية وبوابة الإرسال fail-closed ولا يوجد لها مفتاح تعطيل يتجاوزها؛ هذا مقصود حتى لا يستطيع إعداد تشغيل خاطئ إعادة الهبد. مفاتيح `REPLY_VALIDATOR_ENABLED` و`REPLY_QUALITY_GATE_ENABLED` و`KNOWLEDGE_INJECTION_ENABLED` تبقى للتحكم بالمراحل التوليدية، بينما التحقق الحتمي النهائي يظل إلزاميًا. الرجوع الآمن يكون إلى commit الإصدار السابق، لا تعطيل التحقق مع إبقاء الكود الجديد نصف مفعل.

## إطلاق محدود

1. متجر الاختبار فقط لمدة مراقبة متفق عليها.
2. قياس: block rate، repair rate، clarification rate، duplicate rate، send failures، ووقت الاستجابة.
3. مراجعة يدوية لعينة تشمل أدوبي وفري بيك وإنفاتو والأسئلة الطبيعية والرسائل المتتابعة.
4. اختبار duplicate webhook وretry وإعادة تشغيل worker.
5. توسيع تدريجي إلى متجر واحد منخفض المخاطر، ثم دفعات صغيرة.

## إنذارات الإيقاف

- أي tuple تجاري غير مطابق.
- أي انتقال لسعر أو إعداد أو رسالة بين متجرين أو عميلين.
- أي كشف للهوية الآلية أو اسم موظف غير مفعّل.
- إرسال آلي بلا `validationDecision=validated`.
- ارتفاع التكرار أو الصمت أو التحويلات الخاطئة عن خط الأساس المتفق عليه.
- فشل migration أو تأخر worker أو تضخم traces.

## الرجوع

1. إيقاف توسيع النطاق وإيقاف workers الجديدة.
2. إعادة إصدار التطبيق السابق المعروف، دون استخدام `git reset --hard`.
3. إبقاء الجداول الإضافية مؤقتًا لأنها additive ولا تغيّر السلوك؛ تعطيل `REPLY_TRACE_ENABLED`.
4. إذا تقرر حذف الإضافات لاحقًا، أخذ snapshot ثم تشغيل ملفات rollback بالترتيب العكسي ومراجعة عدد الصفوف قبل كل حذف.
5. إعادة تشغيل worker السابق والتحقق من queue backlog وmessage states.
6. الاحتفاظ بـoperation IDs وآثار الحادثة المنقحة للتحليل.

## ملاحظة مهمة

الرجوع إلى الإصدار السابق يعيد معه عيب خلط حقائق المنتجات. لذلك عند فشل الإطلاق بسبب مشكلة تشغيلية يجب إيقاف الردود التجارية الآلية أو تقييد المتجر الاختباري بدل السماح للإصدار السابق بإعطاء أسعار غير صحيحة للعملاء.
